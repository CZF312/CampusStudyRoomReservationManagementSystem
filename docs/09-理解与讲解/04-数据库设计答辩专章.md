## B. 第7章 规范化与反规范化（7.6）

### <a id="db-b1"></a>B.1 第三范式（3NF）定义与本项目结论

**教材说什么**

- **规范化**：把数据拆成多张表，消除重复。
- **第三范式（3NF）**：在满足 2NF 的前提下，**消除传递函数依赖**——每个非主属性必须**直接**依赖主键，不能通过别的非主属性间接依赖。

**零基础：什么是传递依赖？**

若主键 X 决定 Y，Y 又决定 Z（X→Y→Z），则 Z 对 X 是**传递依赖**。3NF 要求把 Y、Z 拆到不同表，让 Z 只依赖 Y 的主键。

**本项目结论（答辩直接说）**

> **是的，本系统以第三范式（3NF）为主**；同时有 **24 条外键**、**45 个二级索引**、**1 个视图**，满足引用完整性与查询/并发性能。  
> 极少数字段（如 `operation_log.operator_name`）为**审计历史**保留可控反范式，属于工业界常见做法。

### <a id="db-b2"></a>B.2 本项目如何达成 3NF（组长标准答法）

#### ① 消除传递依赖：典型分表

| 改造 | 若不拆会怎样（传递依赖） | 本项目做法 |
|------|------------------------|-----------|
| 账号与档案 | 档案 ID→账号 ID→密码/登录状态 | **`user_account`** + **`student_profile`** 分表 |
| 自习室与管理员 | 自习室 ID→管理员 ID→管理员电话/姓名 | **`study_room.manager_id`** 只存外键，详情在 **`admin_account`** |

#### ② 拆除多值属性（1NF / 2NF）

- 旧设计：设施存成 `"投影仪,空调,插座"` 逗号串 → 违反**原子性（1NF）**。
- 第三版：**`facility`** 字典表 + **`study_room_facility`** 关联表（多对多）。

#### ③ 移除可计算的派生字段（3NF）

- 旧版 `study_room.seat_count`：座位数可由 `COUNT(seat.id)` 算出，留在表里易与座位表增删**不一致**。
- 第三版：**删除 seat_count 等派生列**；需要时用动态 SQL 或视图 `COUNT` 现算（见 [§6](#user-content-db-6)）。

#### ④ 少量反范式（能说清原因即可）

| 字段 | 为何保留 |
|------|----------|
| `operation_log.operator_name` | 管理员改名后，历史日志仍显示**当时**操作者姓名 |

**答辩一句话（3NF）**

> 我们按 3NF 设计 16 表：账号/档案分离、设施拆关联表、去掉 seat_count 等可算字段；外键保证引用完整，详见 [schema.sql](../06-部署配置/schema.sql) 与 [范式说明](../06-部署配置/数据库范式与设计说明.md)。

## C. 第8章 数据库编程

### C.1 SQL 语法（8.1 变量 / 游标 / 控制语句）

**教材**：在 MySQL 里写 `DECLARE`、`CURSOR`、`IF/WHILE`。  
**本项目**：**已使用**。在存储过程 `sp_change_student_credit` 中，我们声明了局部变量 `DECLARE v_before, v_after INT` 以及异常处理器 `EXIT HANDLER`，并使用 `IF/ELSEIF` 控制语句来进行信用分区间过滤（限制在 0 至 500 分之间）以及拉黑条件判断。

### C.2 存储过程与存储函数（8.2）

**教材**：`CREATE PROCEDURE` / `CREATE FUNCTION` 封装在 DB。  
**本项目**：**已实现 1 个存储过程与 1 个自定义函数**。
1. **存储过程 `sp_change_student_credit`**：
   - 作用：联动更新学生信用分、积分流水，以及当信用分低于阈值时，自动插入 `blacklist_record` 并变更用户账号状态为“拉黑”。
   - 优势：把 Java 端原本 5 次独立的数据库 I/O 交互与事务，下沉为数据库底层的原子操作。利用了行锁 `FOR UPDATE`，防高并发下积分扣减的脏读和竞争问题。
   - 后端调用：在 [AppService.java](file:///d:/SCAU/软工8班/专业课资料/大二下/数据库设计实践/CampusStudyRoomReservationManagementSystem/src/main/java/com/scau/campusstudyroomreservationmanagementsystem/service/AppService.java#L2154) 中通过 `CALL sp_change_student_credit(...)` 调用。
2. **自定义函数 `fn_is_seat_reserved`**：
   - 作用：根据传入的座位 ID 和时间，自动在 `reservation_slot` 表中匹配其被占用状态（返回 `1` 占用，`0` 空闲）。
   - 优势：将复杂的子查询封装为数据库函数，简化多表查询中的嵌套语法。

### C.3 触发器（8.3）

**教材**：`BEFORE INSERT` 自动改数据。  
**本项目**：**无触发器**。例如「两人抢同一座位」靠 **uk_seat_slot 唯一索引** + Java 捕获重复键，不靠触发器。  
**答辩**：「并发控制在应用层事务 + 数据库唯一约束，没有用触发器。」

### C.4 在程序中使用数据库（8.4 JDBC / 框架）

**教材层次**：

1. **ODBC/JDBC**：Java 通过标准接口连 MySQL（底层）。
2. **框架连接**：Spring Boot 提供 **DataSource + JdbcTemplate**，不用手写连接关闭。

**本项目链路**：

```
AppController 收到 HTTP
  → AppService 方法
    → jdbcTemplate.query / update("SQL ...", 参数)
      → MySQL InnoDB 执行
```

**文件**：[AppService.java](https://github.com/CZF312/CampusStudyRoomReservationManagementSystem/blob/master/src/main/java/com/scau/campusstudyroomreservationmanagementsystem/service/AppService.java) · 配置在 `application.properties`（数据源 URL、用户名密码）。

**答辩一句话**：「我们属于教材 8.4.2 JDBC + 8.4.3 框架（Spring），没有用嵌入式 SQL。」

## D. 第9章 数据库存储与索引

### D.1 存储引擎（9.1）

**教材**：MySQL 有多种引擎；**InnoDB** 支持事务、行级锁、外键。  
**本项目**：全部表 **`ENGINE=InnoDB`**（见 schema.sql 每张表末尾）。  
**和课设关系**：预约、签到要 **事务**（要么全成功要么全失败），必须用 InnoDB，不能用老的 MyISAM。

### D.2 索引（9.2）

**教材概念**：


| 概念         | 零基础解释                      | 本项目                                         |
| ---------- | -------------------------- | ------------------------------------------- |
| **索引**     | 像字典目录，加快按某列查找              | 每张表在 user_id、status、日期等列上有 `KEY`            |
| **B+ 树索引** | MySQL InnoDB 默认索引结构，适合范围查询 | 所有 `KEY`/`PRIMARY KEY` 底层都是 B+ 树            |
| **唯一索引**   | 索引 + 不允许重复                 | **uk_seat_slot(seat_id, slot_start)** 防双占 |
| **哈希索引**   | 只适合等值查                     | 本项目 **未单独建 HASH 索引**，用 B+ 树                 |


**必背例子**：两人同时预约 A-12 座 14:00–14:10 → 两个事务都 INSERT `reservation_slot` → 第二个撞 **唯一索引** → 失败 → Java 返回「已被预约」。这就是教材 **9.2 索引** + **11 章并发** 的结合。

## F. 第11章 事务与并发控制

### F.1 事务与 ACID（11.1）

**教材**：事务 = 一组 SQL 要么全做要么全不做。


| 特性        | 含义        | 本项目例子                                                          |
| --------- | --------- | -------------------------------------------------------------- |
| **A 原子性** | 全成功或全回滚   | 预约：写 `reservation` + 多条 `slot` + 发通知，任一失败则 `@Transactional` 回滚 |
| **C 一致性** | 数据满足规则    | 外键 + 唯一索引 + 业务校验（信用分不够不能预约）                                    |
| **I 隔离性** | 事务之间少互相干扰 | InnoDB 默认隔离级别；抢座靠唯一键                                           |
| **D 持久性** | 提交后落盘     | InnoDB redo log（答辩可说「提交后 MySQL 保证持久化」）                         |


**代码**：`AppService.createReservation` 等方法上的 **`@Transactional`**（Spring 开启事务）。

### F.2 并发控制（11.3）与隔离级别（11.4）

**教材**：多人同时改同一行要用 **锁**；隔离级别决定「能看见别的事务改了一半的数据吗」。

**本项目策略（两层）**：

1. **应用层**：Spring 事务 + 先查后写（如检查 status=待使用再签到）。
2. **数据库层**：**唯一索引 `uk_seat_slot`** — 教材里的「锁」在抢座场景由 **唯一约束冲突** 体现，更简单也更好讲。

**答辩话术**：

> 并发主要靠 InnoDB 行锁和 `uk_seat_slot` 唯一索引；预约创建在 `@Transactional` 里，冲突时捕获 `DuplicateKeyException`。没有用 MySQL 的存储过程或触发器做并发。

### F.3 恢复（11.5）

**教材**：用 **日志** 在崩溃后恢复。  
**本项目**：依赖 InnoDB 自带 redo/undo；**业务上不手写恢复脚本**。答辩可说：「演示环境用 start.bat 导完整库 `database-full.sql` 即可重建。」

## 4. 外键 24 条（逐条能答）

**外键是什么（零基础）**：子表的某一列必须是父表已存在的主键值；防止「预约指向不存在的座位」这类脏数据。

**本库 24 条一览**（打开 schema.sql 可对照 `CONSTRAINT fk_`）：


| #   | 约束名                         | 子表 → 父表                                          | 业务含义        |
| --- | --------------------------- | ------------------------------------------------ | ----------- |
| 1   | `fk_student_profile_user`   | student_profile.user_id → user_account.id        | 档案必须属于某学生账号 |
| 2   | `fk_study_room_manager`     | study_room.manager_id → admin_account.id         | 每室可有负责管理员   |
| 3   | `fk_room_facility_room`     | study_room_facility.room_id → study_room.id      | 关联表挂房间      |
| 4   | `fk_room_facility_facility` | study_room_facility.facility_id → facility.id    | 关联表挂设施      |
| 5   | `fk_seat_room`              | seat.room_id → study_room.id                     | 座位必须属于某自习室  |
| 6   | `fk_reservation_user`       | reservation.user_id → user_account.id            | 预约必须有学生     |
| 7   | `fk_reservation_room`       | reservation.room_id → study_room.id              | 预约必须指向有效房间  |

| 12  | `fk_checkin_user`           | checkin_record.user_id → user_account.id         | 签到对应学生      |
| 13  | `fk_checkin_admin`          | checkin_record.admin_id → admin_account.id       | 记录哪个管理员操作   |
| 14  | `fk_credit_user`            | credit_log.user_id → user_account.id             | 信用流水归属学生    |
| 15  | `fk_credit_reservation`     | credit_log.reservation_id → reservation.id       | 流水可关联预约     |

| 20  | `fk_feedback_user`          | feedback_ticket.user_id → user_account.id        | 反馈人         |
| 21  | `fk_feedback_reservation`   | feedback_ticket.reservation_id → reservation.id  | 可选关联预约      |
| 22  | `fk_feedback_room`          | feedback_ticket.room_id → study_room.id          | 可选关联房间      |
| 23  | `fk_feedback_seat`          | feedback_ticket.seat_id → seat.id                | 可选关联座位      |
| 24  | `fk_feedback_handler`       | feedback_ticket.handler_id → admin_account.id    | 处理人         |


**老师追问「删父行会怎样？」**

- 多数外键 **未写 ON DELETE CASCADE** → 有子行时删父行会 **报错**，保护数据。
- 例外：`study_room_facility`、`seat`（→ room）、`reservation_slot`、`checkin_record` 等对 room/reservation 用了 **ON DELETE CASCADE** → 删预约会级联删时间片/签到，避免孤儿行。

**答辩短答**：「我们一共 24 个外键，覆盖学生—预约—座位—房间—管理员的主链路；核心是保证引用完整，不能预约不存在的 seat_id。」

## 5. 索引与唯一约束（逐条能答）

**索引是什么（零基础）**：给常用查询列建「目录」，加快 WHERE / JOIN；**唯一索引**还能在数据库层禁止重复。

### 5.1 必须会讲的 3 个「业务级」唯一索引


| 索引名              | 表                | 列                     | 答辩要点                                                                                           |
| ---------------- | ---------------- | --------------------- | ---------------------------------------------------------------------------------------------- |
| **uk_seat_slot** | reservation_slot | (seat_id, slot_start) | **防并发双占**：两人同时抢同座同一 10 分钟片，第二个 INSERT 失败；Java 在 `createReservation` 捕获 `DuplicateKeyException` |
| `reservation_no` | reservation      | reservation_no        | 16 位预约号全局唯一                                                                                    |
| `uk_room_seat`   | seat             | (room_id, seat_no)    | 同一室内座位号不重复                                                                                     |
| `student_no`     | student_profile  | student_no            | 12 位学号唯一                                                                                       |


### 5.2 按表汇总（二级索引）


| 表                    | 索引（节选）                                                                  | 用途                |
| -------------------- | ----------------------------------------------------------------------- | ----------------- |
| user_account         | idx_user_role_status                                                    | 按角色/状态筛用户         |
| student_profile      | idx_student_audit_status, idx_student_college_major                     | 审核列表、院系统计         |

## 6. 视图

> **索引 + 外键 + 视图** 共同支撑 3NF 下的**引用完整性**与**查询性能**；视图负责「固定口径的统计模板」，复杂报表则在 Java 里动态 SQL（见 §6.2–§6.3）。

### <a id="db-6-1"></a>6.1 `v_room_daily_usage` 定义与作用

| 项 | 说明 |
|----|------|
| 定义位置 | [schema.sql L330-L341](../06-部署配置/schema.sql#L330-L341) |
| 算什么 | 每个自习室 **当天（curdate()）** 的：座位数 `seat_count`、预约数 `reservation_count`、实际使用数 `used_count`、**使用率 `usage_rate`** |
| 核心 SQL | `study_room` LEFT JOIN `seat` LEFT JOIN `reservation`，且 **`r.reserve_date = curdate()`** 写死在视图内 |
| 设计目的 | **避免在 `study_room` 表维护冗余计算字段**（如 seat_count、今日使用率），符合 3NF——需要时查视图或动态 SQL 现算 |

**视图是什么（零基础）**：保存好的 SELECT，查询时像虚拟表；本库只有这一个，没有物化视图。

**答辩演示**：可在 MySQL 客户端执行 `SELECT * FROM v_room_daily_usage;` 向老师展示「今日各室使用率」。

### <a id="db-6-2"></a>6.2 运行时为何不用视图做报表？

**老师常问**：「有视图为什么管理端统计不用它？」

| 原因 | 说明 |
|------|------|
| **日期写死为「今日」** | 视图内 `r.reserve_date = curdate()`，**只能统计当天**，无法查上周/上月/自定义区间 |
| **视图不能传参** | 视图是静态 SQL 模板，**不能**接收前端的 `period`、`rangeMode`、`startDate`/`endDate` |
| **报表维度多** | F6.1 要峰值、趋势、信用、CSV 导出等；F5.1 学生端也要当期/往期——都需**动态时间窗** |

**结论**：`v_room_daily_usage` 用于**验收展示 / 答辩速查今日使用率**；**管理端与学生端复杂统计不走此视图**。

### <a id="db-6-3"></a>6.3 统计报表实际怎么实现？

**入口**：`AppService.statisticsUsage`（及 `statisticsReport` 打包多类统计）

代码位置：[AppService.java L1103-L1120](https://github.com/CZF312/CampusStudyRoomReservationManagementSystem/blob/master/src/main/java/com/scau/campusstudyroomreservationmanagementsystem/service/AppService.java#L1103-L1120)

**流程（与视图逻辑类似，但时间条件可变）**

1. **动态参数**：`resolveStatsRange(rangeMode, startDate, endDate)` + `reservationDateJoinCondition(period, …)` 在内存中算出 `dateJoin`（周/月/年或自选起止日）。
2. **动态 SQL**：JdbcTemplate 执行与视图**同构**的 JOIN 聚合——`study_room` + `seat` + `reservation`，统计 seatCount / reservationCount / usedCount / usageRate。
3. **关键差异**：`LEFT JOIN reservation r ON … AND {dateJoin}` 中的 **dateJoin 随用户选择变化**，而非写死 `curdate()`。

```text
视图：     … AND r.reserve_date = curdate()          ← 永远「今天」
报表 SQL： … AND {dateJoin}                        ← 周/月/年/往期/自定义
```

**答辩短答（视图 + 报表）**

> 有一个视图 **`v_room_daily_usage`**，固定算**今日**各室使用率，定义在 schema.sql L330–L341，答辩可 `SELECT *` 演示。  
> 管理端 F6.1、学生端 F5.1 的周报/月报/自定义日期**不用视图**，因为视图不能传动态时间参数；我们在 **`AppService.statisticsUsage`** 里用 JDBC **动态拼 SQL**，JOIN 逻辑与视图类似，但 `dateJoin` 随前端 `period`、`rangeMode`、`startDate`/`endDate` 变化。

## 9. 口述模板（30 秒版）

### Q：你们有没有外键？

> 有，24 条。比如 `reservation.seat_id` 外键指向 `seat.id`，保证不能预约不存在的座位；`reservation_slot` 通过 `uk_seat_slot` 唯一索引和外键一起保证同座同时间片不重复。定义都在 `docs/06-部署配置/schema.sql`。

### Q：有没有索引？最重要的哪个？

> 每张表在常用查询列上都有二级索引，比如 `reservation` 的 `(user_id, reserve_date)`。最重要的是 `reservation_slot` 上的唯一索引 **uk_seat_slot(seat_id, slot_start)**，用来防止两人同时预约同一座位同一时间段，这是数据库层并发控制。

### Q：有没有视图？为什么报表不用视图？

> 有 **1 个**视图 **`v_room_daily_usage`**（schema.sql L330–L341），动态算各室**今日**座位数、预约数、使用率，避免在自习室表存冗余计算字段。  
> 管理端/学生端周报、月报、自定义起止日**不用它**，因为视图里日期写死 `curdate()` 且不能传参；报表在 **`AppService.statisticsUsage`** 里动态拼 SQL，JOIN 逻辑类似但时间条件随 `period`、`rangeMode`、`startDate`/`endDate` 变化。

### Q：满足第三范式吗？

> **以 3NF 为主**：账号/档案分表、设施拆关联表、去掉 seat_count 等可算字段；**24 条外键**保证引用完整，**45 个二级索引**（含 **uk_seat_slot** 防抢座）保证查询与并发。少量反范式如 `operation_log.operator_name` 只为审计保留历史姓名。

### Q：这个功能代码怎么实现的？（演示被打断）

> 浏览器 `App.vue` 调 `POST /api/...` → `AppController` 转发 → `AppService.xxx` 里 JdbcTemplate 执行 SQL 改 **表名** → 事务 `@Transactional` 保证要么全成功要么回滚。我可以打开 GitHub 行号，首行 `【Fx-y】` 注释就是总体讲解。
