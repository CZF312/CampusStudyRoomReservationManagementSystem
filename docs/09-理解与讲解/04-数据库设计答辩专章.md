## B. 第7章 规范化与反规范化（7.6）

### 教材说什么

- **规范化**：把数据拆成多张表，消除重复。例如：不要把「学院名」在每个学生行里抄一遍，而是学生表只存 `student_id`，学院名单独一张表。
- **第三范式（3NF）**：非主键字段不能只依赖「另一个非主键字段」（消除传递依赖）。
- **反规范化**：有时故意冗余一点换查询速度（本项目很少）。

### 本项目怎么做


| 教材问题       | 本项目的答法                                        | 例子      |
| ---------- | --------------------------------------------- | ------- |
| 有没有重复字段？   | 设施从「逗号串」拆成 `facility` + `study_room_facility` | F7.2    |
| 有没有可算出来的列？ | 不存「座位总数」，用 `COUNT(seat)` 现算                   | 3NF     |
| 有没有故意冗余？   | `operation_log.operator_name` 保留当时姓名          | 反范式，为审计 |


### 答辩一句话

> 我们按第三范式设计 16 张表，设施多对多拆表；信用、预约状态等用外键和 CHECK 保证一致，详见 schema.sql 和范式说明文档。

## C. 第8章 数据库编程

### C.1 SQL 语法（8.1 变量 / 游标 / 控制语句）

**教材**：在 MySQL 里写 `DECLARE`、`CURSOR`、`IF/WHILE`。  
**本项目**：**不在数据库存过程序**，所有 `SELECT/INSERT/UPDATE` 写在 **`AppService.java`** 的字符串里，由 **JdbcTemplate** 执行。  
**为什么**：课设业务会变（报表、取消规则），改 Java 比改存储过程好调试，答辩也能直接指行号。

### C.2 存储过程与存储函数（8.2）

**教材**：`CREATE PROCEDURE` / `CREATE FUNCTION` 封装在 DB。  
**本项目**：**无**。一个业务动作 = 一个 Java 方法，例如 `createReservation()` 里连续多条 SQL。  
**对应关系**：教材里的「存储过程」≈ 我们的 **`AppService.xxx()`**。

### C.3 触发器（8.3）

**教材**：`BEFORE INSERT` 自动改数据。  
**本项目**：**无触发器**。例如「两人抢同一座位」靠 **uk_seat_slot 唯一索引** + Java 捕获重复键，不靠触发器。  
**答辩**：「并发控制在应用层事务 + 数据库唯一约束，没有用触发器。」

### C.4 在程序中使用数据库（8.4 JDBC / 框架）

**教材层次**：

1. **ODBC/JDBC**：Java 通过标准接口连 MySQL（底层）。
2. **框架连接**：Spring Boot 提供 **DataSource + JdbcTemplate**，不用手写连接关闭。

**本项目链路**：

```
AppController 收到 HTTP
  → AppService 方法
    → jdbcTemplate.query / update("SQL ...", 参数)
      → MySQL InnoDB 执行
```

**文件**：[AppService.java](https://github.com/CZF312/CampusStudyRoomReservationManagementSystem/blob/master/src/main/java/com/scau/campusstudyroomreservationmanagementsystem/service/AppService.java) · 配置在 `application.properties`（数据源 URL、用户名密码）。

**答辩一句话**：「我们属于教材 8.4.2 JDBC + 8.4.3 框架（Spring），没有用嵌入式 SQL。」

## D. 第9章 数据库存储与索引

### D.1 存储引擎（9.1）

**教材**：MySQL 有多种引擎；**InnoDB** 支持事务、行级锁、外键。  
**本项目**：全部表 **`ENGINE=InnoDB`**（见 schema.sql 每张表末尾）。  
**和课设关系**：预约、签到要 **事务**（要么全成功要么全失败），必须用 InnoDB，不能用老的 MyISAM。

### D.2 索引（9.2）

**教材概念**：


| 概念         | 零基础解释                      | 本项目                                         |
| ---------- | -------------------------- | ------------------------------------------- |
| **索引**     | 像字典目录，加快按某列查找              | 每张表在 user_id、status、日期等列上有 `KEY`            |
| **B+ 树索引** | MySQL InnoDB 默认索引结构，适合范围查询 | 所有 `KEY`/`PRIMARY KEY` 底层都是 B+ 树            |
| **唯一索引**   | 索引 + 不允许重复                 | **uk_seat_slot(seat_id, slot_start)** 防双占 |
| **哈希索引**   | 只适合等值查                     | 本项目 **未单独建 HASH 索引**，用 B+ 树                 |


**必背例子**：两人同时预约 A-12 座 14:00–14:10 → 两个事务都 INSERT `reservation_slot` → 第二个撞 **唯一索引** → 失败 → Java 返回「已被预约」。这就是教材 **9.2 索引** + **11 章并发** 的结合。

详情：[§5 索引清单](#user-content-db-5)

## E. 第10章 查询处理与优化

### 教材说什么

- **选择运算（10.2.1）**：`WHERE status='待使用'` 过滤行。  
- **连接运算（10.2.2）**：多表 `JOIN`，例如预约表 JOIN 用户表 JOIN 座位表。  
- **代数优化（10.3）**：数据库自动选较优执行顺序（你不用手写）。

### 本项目例子


| 业务    | SQL 形态                                                            | Java 位置                   |
| ----- | ----------------------------------------------------------------- | ------------------------- |
| 我的预约  | `SELECT ... FROM reservation r JOIN seat s ... WHERE r.user_id=?` | `listMyReservations`      |
| 管理端报表 | 多表 JOIN + `GROUP BY` + 动态日期条件                                     | `statisticsReport` · F6.1 |
| 学习统计  | `TIMESTAMPDIFF` + 时间窗 WHERE                                       | `myStudyDuration` · F5.1  |


**注意**：管理端 **复杂报表不用视图** `v_room_daily_usage`，而是 Service 里 **动态拼 SQL**（教材 10 章「查询实现」在 Java 里完成）。

**答辩一句话**：「查询主要是 AppService 里的 JDBC：单表 WHERE 是选择运算，报表是多表 JOIN；优化交给 MySQL 优化器。」

## F. 第11章 事务与并发控制

### F.1 事务与 ACID（11.1）

**教材**：事务 = 一组 SQL 要么全做要么全不做。


| 特性        | 含义        | 本项目例子                                                          |
| --------- | --------- | -------------------------------------------------------------- |
| **A 原子性** | 全成功或全回滚   | 预约：写 `reservation` + 多条 `slot` + 发通知，任一失败则 `@Transactional` 回滚 |
| **C 一致性** | 数据满足规则    | 外键 + 唯一索引 + 业务校验（信用分不够不能预约）                                    |
| **I 隔离性** | 事务之间少互相干扰 | InnoDB 默认隔离级别；抢座靠唯一键                                           |
| **D 持久性** | 提交后落盘     | InnoDB redo log（答辩可说「提交后 MySQL 保证持久化」）                         |


**代码**：`AppService.createReservation` 等方法上的 **`@Transactional`**（Spring 开启事务）。

### F.2 并发控制（11.3）与隔离级别（11.4）

**教材**：多人同时改同一行要用 **锁**；隔离级别决定「能看见别的事务改了一半的数据吗」。

**本项目策略（两层）**：

1. **应用层**：Spring 事务 + 先查后写（如检查 status=待使用再签到）。
2. **数据库层**：**唯一索引 `uk_seat_slot`** — 教材里的「锁」在抢座场景由 **唯一约束冲突** 体现，更简单也更好讲。

**答辩话术**：

> 并发主要靠 InnoDB 行锁和 `uk_seat_slot` 唯一索引；预约创建在 `@Transactional` 里，冲突时捕获 `DuplicateKeyException`。没有用 MySQL 的存储过程或触发器做并发。

### F.3 恢复（11.5）

**教材**：用 **日志** 在崩溃后恢复。  
**本项目**：依赖 InnoDB 自带 redo/undo；**业务上不手写恢复脚本**。答辩可说：「演示环境用 start.bat 导完整库 `database-full.sql` 即可重建。」

## 4. 外键 24 条（逐条能答）

**外键是什么（零基础）**：子表的某一列必须是父表已存在的主键值；防止「预约指向不存在的座位」这类脏数据。

**本库 24 条一览**（打开 schema.sql 可对照 `CONSTRAINT fk_`）：


| #   | 约束名                         | 子表 → 父表                                          | 业务含义        |
| --- | --------------------------- | ------------------------------------------------ | ----------- |

**老师追问「删父行会怎样？」**

- 多数外键 **未写 ON DELETE CASCADE** → 有子行时删父行会 **报错**，保护数据。
- 例外：`study_room_facility`、`seat`（→ room）、`reservation_slot`、`checkin_record` 等对 room/reservation 用了 **ON DELETE CASCADE** → 删预约会级联删时间片/签到，避免孤儿行。

**答辩短答**：「我们一共 24 个外键，覆盖学生—预约—座位—房间—管理员的主链路；核心是保证引用完整，不能预约不存在的 seat_id。」

## 5. 索引与唯一约束（逐条能答）

**索引是什么（零基础）**：给常用查询列建「目录」，加快 WHERE / JOIN；**唯一索引**还能在数据库层禁止重复。

### 5.1 必须会讲的 3 个「业务级」唯一索引


| 索引名              | 表                | 列                     | 答辩要点                                                                                           |
| ---------------- | ---------------- | --------------------- | ---------------------------------------------------------------------------------------------- |
| **uk_seat_slot** | reservation_slot | (seat_id, slot_start) | **防并发双占**：两人同时抢同座同一 10 分钟片，第二个 INSERT 失败；Java 在 `createReservation` 捕获 `DuplicateKeyException` |
| `reservation_no` | reservation      | reservation_no        | 16 位预约号全局唯一                                                                                    |
| `uk_room_seat`   | seat             | (room_id, seat_no)    | 同一室内座位号不重复                                                                                     |
| `student_no`     | student_profile  | student_no            | 12 位学号唯一                                                                                       |


### 5.2 按表汇总（二级索引）


| 表                    | 索引（节选）                                                                  | 用途                |
| -------------------- | ----------------------------------------------------------------------- | ----------------- |
| user_account         | idx_user_role_status                                                    | 按角色/状态筛用户         |
| student_profile      | idx_student_audit_status, idx_student_college_major                     | 审核列表、院系统计         |
| study_room           | idx_room_manager, idx_room_status                                       | 管理员辖室、开放状态        |
| seat                 | idx_seat_room_status, idx_seat_feature                                  | 选座过滤可用/电源/靠窗      |
| reservation          | idx_res_user_date, idx_res_room_date, idx_res_seat_date, idx_res_status | 我的预约、按室/座/日查、状态筛选 |
| reservation_slot     | idx_slot_reservation                                                    | 按预约查占用片           |
| checkin_record       | idx_checkin_admin_time, idx_checkin_user_time                           | 管理端/学生签到历史        |
| credit_log           | idx_credit_user_time, idx_credit_type, idx_credit_reservation           | 信用流水查询            |
| blacklist_record     | idx_blacklist_user_status, idx_blacklist_end_status                     | 黑名单与自动解除          |
| announcement         | idx_announcement_status_time, idx_announcement_room, …                  | 公告列表              |
| notification_message | idx_notification_user_read, idx_notification_user_time                  | 未读角标、时间排序         |
| feedback_ticket      | idx_feedback_status, idx_feedback_user_time, …                          | 工单处理              |
| operation_log        | idx_op_log_operator, idx_op_log_module                                  | 审计查询              |


**完整列表**：在 `schema.sql` 中搜索 `KEY` / `UNIQUE KEY`（约 69 行定义；实际 **45 个**二级索引，复合索引占多行）。可用 `verify-v3-dictionary.ps1` 验 16 表/24 外键/1 视图。

**答辩短答**：「索引主要加在外键列、状态列、时间列和用户 id 上，保证列表和统计查询速度；最重要的是 `uk_seat_slot`，用唯一索引实现抢座互斥。」

## 9. 口述模板（30 秒版）

### Q：你们有没有外键？

> 有，24 条。比如 `reservation.seat_id` 外键指向 `seat.id`，保证不能预约不存在的座位；`reservation_slot` 通过 `uk_seat_slot` 唯一索引和外键一起保证同座同时间片不重复。定义都在 `docs/06-部署配置/schema.sql`。

### Q：有没有索引？最重要的哪个？

> 每张表在常用查询列上都有二级索引，比如 `reservation` 的 `(user_id, reserve_date)`。最重要的是 `reservation_slot` 上的唯一索引 **uk_seat_slot(seat_id, slot_start)**，用来防止两人同时预约同一座位同一时间段，这是数据库层并发控制。

### Q：有没有视图？

> 有一个 **`v_room_daily_usage`**，统计各自习室今日座位数、预约数和使用率，在 schema.sql 第 330 行左右。管理端复杂报表是 Java 里 JDBC 动态 SQL，不是查这个视图。

### Q：这个功能代码怎么实现的？（演示被打断）

> 浏览器 `App.vue` 调 `POST /api/...` → `AppController` 转发 → `AppService.xxx` 里 JdbcTemplate 执行 SQL 改 **表名** → 事务 `@Transactional` 保证要么全成功要么回滚。我可以打开 GitHub 行号，首行 `【Fx-y】` 注释就是总体讲解。
